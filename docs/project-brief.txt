The product in one sentence
CareSignal highlights what a shift note documents about human help for a selected walk, then compares that evidence with a staff-confirmed description of the resident’s usual help when one is available.

2. Product scope and goals
User and moment
An incoming memory-care aide reads a fictional resident’s shift note during handoff. The aide wants to know whether the note describes a staff member walking beside the resident, hands-on help, or independent walking for one specific event. When there is a recorded usual level for the same walk, the aide can review how the new observation compares.
What matters most
1. One event. Tie the finding to the selected resident, walk and observation date. Notes can describe multiple people, activities and times.
2. One verifiable finding. Use the words in the note to support the label. Allow the evidence to span adjacent sentences when that is what a human reviewer needs.
3. One optional comparison. Use a structured baseline confirmed for that resident and context. The model reads the note. Code compares the levels.
4. One active source. A correction replaces the note used for the finding. The original is still available as history.
5. One reproducible experiment. Quantify how often the AI and a simple phrase matcher get both the assistance label and its evidence right on held-out Fruta notes.
Boundaries for this prototype
The intended evaluation set is public synthetic Fruta data. Demo residents and custom walkthrough inputs are fictional. The product reports what the documentation says about walking assistance. Design the UI around evidence review and handoff. Treat clinical interpretation, urgency, fall-risk scoring, treatment, production patient records, and integration with clinical systems as outside this prototype’s scope. Carry this sentence into the app and submitted write-up verbatim.
This project is a prototype and is not medical advice.

Main flows
Analyze a note
1. Select a fictional resident, date, canonical walk and optional target cue such as “outbound walk this morning.”
2. Paste or load the complete note. For a public preset, show the dataset and note ID.
3. Submit Analyze note. Store the observation and active note. Run the selected adapter for that revision.
4. Show Documented help with the validated evidence. If a compatible baseline is present, show the comparison and give the aide access to both sources.
5. On an adapter failure, show a retry action scoped to the same revision. If the user switches cases before a result returns, render only the selected case.
Confirm usual assistance
1. Select Set usual assistance from the active case.
2. Show the resident and walking context as part of the form. Require one of the three specific levels, a short source description and a confirmation date. If a provided description and its selected level conflict, the user must resolve the description before treating it as confirmed. For the first release, use a level field and explicit confirmation step that displays both values for checking. A free-text baseline never sets the rank by itself.
3. Save the confirmation. Recompute the comparison from the existing validated finding. This edit does not require an additional model call.
4. Show the confirmation date and the source text on the card. An empty baseline is normal. The extraction result still gives the aide something to review.
Attach a replacement
1. Open Attach replacement from the active note. Show the original revision number and text so the aide can confirm the target.
2. Explain the action in one sentence. “This replacement becomes the source for the current card. The previous note stays in history.”
3. Require nonblank replacement text. Commit it as a new full version of the note for the same observation case.
4. Immediately invalidate the previous card and its highlighted excerpt. Show Analyzing replacement until the new result arrives.
5. With missing evidence, show Unclear and cite the replacement as the active source. With an error, show a retryable error. The previous flag stays cleared in either case.

5. Assistance taxonomy and attribution
The five extraction labels
Enum	UI label	Gold-label rule
INDEPENDENT	Independent	The note explicitly says the resident walked unaided or on their own for the selected event, with any device listed separately.
SUPERVISION	Staff beside or supervising	The note describes a person accompanying, staying alongside or supervising for walking support or safety during the selected event. A person’s presence by itself is insufficient.
HANDS_ON	Hands-on help	The note describes physical support given to the resident during the walk, such as holding their arm or steadying them while walking.
HELP_UNSPECIFIED	Help documented, type unspecified	The note establishes that a person helped on this walk. The evidence leaves supervision versus physical support unresolved, or specifies a form of help outside those ranked levels, such as verbal cueing alone.
UNCLEAR	Unclear	The note leaves help ambiguous or unspecified, conflicts about the selected walk, or describes a different person, activity or time.


Annotation and extraction policy
- Anchor the target first. Read the selected resident, date, canonical context and optional cue. In a resident-specific note, an unambiguous pronoun may refer to that resident. Explicit mentions of roommates or other residents override that default.
- Extract the documented event. Distinguish what happened from plans, general ability, recommendations, future intentions and declined or unavailable help. The fictional phrase “needed an aide beside her on the way to breakfast” is accepted as a report of the level documented for that completed trip. An explicit statement that the help was absent controls the label when the note describes what actually happened.
- Bind assistance to walking. Getting out of bed, transfers, dressing, eating and wheelchair transport are distinct from the walking event. Setting up or mentioning a walker is a device detail. Interpreting a general need for assistance as walking help creates false flags.
- Distinguish route and time. Outbound breakfast, return from breakfast and a later lunch walk are separate events. Do the same for yesterday versus the current observation. When the target is still ambiguous, return UNCLEAR with a reason.
- Recognize supervision even when the person can walk unaided. General ability can coexist with a staff member keeping close for fall prevention on a documented walk. If the note clearly describes both during that event, code the documented supervision. If the descriptions contradict each other and attribution cannot resolve the conflict, use UNCLEAR.
- Use the highest supported help level within one event. Explicit hands-on support during the selected walk is sufficient for HANDS_ON even if a staff member also walked alongside at other moments in that same walk. Evidence from a different event does not contribute.
- Preserve modality and negation. “Nobody helped her” can support independence when it describes the completed walk. “I didn’t see whether anyone helped” leaves the help unknown. “I would have held her arm if she needed it” describes a conditional.
- Preserve ambiguous language in translation. A Dutch term like begeleiding can indicate accompaniment or guidance without resolving whether there was physical contact. Use the surrounding source text before assigning a specific level.
Ranking for the comparison
The rank is an internal rule for this prototype. It orders the three specific documentation categories. It does not encode severity or a medical recommendation.
Level	Rank
Independent	0
Staff beside or supervising	1
Hands-on help	2


Only compare a completed, validated extraction and a confirmed baseline for the same resident and canonical context. For a historical observation, use a baseline confirmed by the observation date. The active extraction must belong to the active note revision. Preserve the baseline ID and the confirmation date behind any displayed comparison. Return UNCLEAR for an unspecified type or an ineligible baseline. Render the extracted label separately whenever it is available.
def compare_assistance(observed_rank: int, usual_rank: int) -> str:
    if observed_rank > usual_rank:
        return "MORE_HELP"
    if observed_rank < usual_rank:
        return "LESS_HELP"
    return "MATCHES"
The service checks comparability before calling this pure function. Keep the eligibility check, comparison calculation and user-facing wording independently testable.

Context catalog
Start with to_breakfast, from_breakfast, hallway_walk, garden_walk, walking_attempt and other_walk. The first four represent comparable contexts when selected consistently. walking_attempt and other_walk support extraction and use UNCLEAR for comparison unless the repo later introduces a specific matching context. Treat an optional target cue as part of event selection. Its presence alone never upgrades a generic context into a comparable one.
Storage and service boundaries
- Enable SQLite foreign keys on each connection. Use parameterized queries. Keep the database in a configured local data directory outside source control.
- Scope repository reads and writes to a workspace and verify case ownership before following source pointers. A default launch is a local demo. If opened to a shared audience, use isolated per-session demo workspaces with fictional data. The app should explicitly state which persistence behavior it supports.
- Keep active_revision_id on the case as the source of truth. Validate that any linked revision belongs to that case. Add UNIQUE(case_id, version) and checks for supported enum values.
- Select the latest baseline for the same resident/context with confirmed_on <= observed_on, ordered by confirmed_on then saved_at. Treat confirmation dates as date granularity. Display the exact baseline used so a reviewer can check it.
- Preserve provenance for public presets. Store the Fruta note ID, dataset revision and translation identifiers in the source manifest. The rendered evidence links to the frozen English text and can expose the Dutch original separately.
- Read and write via a service layer. Streamlit screen code should call functions such as create_case, confirm_usual_assistance, analyze_active_revision, replace_active_revision and get_handoff_view. The notebook can call the pure extraction and evaluation functions directly.
Replacement integrity
Use a short transaction to verify that the expected original revision is still active, insert the new revision and update the case pointer. If the active pointer changed, return a conflict and show the latest note before the user retries. If insertion or pointer update fails, roll back both. Begin the model call after the transaction commits.

On completion, associate the result with the exact revision requested. Before rendering, re-read the active pointer and check it against the result revision. If another correction became active during inference, the earlier result remains associated with history. A retry reads the active note again, avoids old input, and preserves the revision history.
